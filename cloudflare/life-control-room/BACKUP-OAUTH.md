# Google Drive backup authorization — issue #22

Status: implementation candidate, disabled by default, not deployed. OAuth authorization
is not a backup or restore PASS. No Drive folder/file creation, D1 export, backup schedule,
retention deletion, or restore is performed by this change.

## Ownership and reference selection

This extends the existing cockpit's deterministic integration boundary, not an agent runtime,
new project container, or authority over another project's data. No other repository is changed.
The architectural review of the existing cockpit's location remains a separate governance issue;
this change does not resolve or waive it.

Base: existing Life Control Room Worker, main `4c94fd0beed7342edad5e0d03576383ad229dfcc`.
Existing project starter: official Cloudflare d1-template, as recorded in README.
For this extension, use Google's documented confidential web-server HTTP OAuth endpoints:
https://developers.google.com/identity/protocols/oauth2/web-server
and Drive account verification:
https://developers.google.com/workspace/drive/api/reference/rest/v3/about/get
References retrieved 2026-10-15. No OAuth server, account-login framework, or additional
Cloudflare service is introduced. The browser-only Google SDK is not used server-side.
Native fetch and Web Crypto keep compatibility with the existing dependency-free Worker;
bounded provider responses, timeouts and fixed HTTPS endpoints limit the adapter surface.

## Provisioning required before use

1. In a Google Cloud project controlled by the owner, enable Google Drive API.
2. Configure Google Auth Platform branding, audience and consent. Create a **Web application**
   OAuth client. Register exactly `https://aios.soliwkr.pro/api/backup/google/callback`.
   A stage client must register its stage host separately. Do not bypass Cloudflare Access
   for callback: the same authenticated owner session must return from Google.
3. Set the following through protected Cloudflare secret entry, never chat/repository/logs:
   - `BACKUP_GOOGLE_CLIENT_ID`, `BACKUP_GOOGLE_CLIENT_SECRET`;
   - `BACKUP_TARGET_EMAIL`: approved SOLIWKR Google account;
   - `BACKUP_FORBIDDEN_EMAIL`: current Trovatemi Google account, mandatory;
   - `BACKUP_FORBIDDEN_ACCOUNT_ID`: Trovatemi Drive permissionId if securely available;
   - `BACKUP_OAUTH_SEAL_KEY`: independent random 32-byte AES key, standard base64.
   Email checks normalize Gmail dots, plus aliases and googlemail.com.
4. Review/apply additive `0006_backup_oauth.sql` in fixture stage first. Production application
   requires the controlled release gate. Never reapply the entire migration chain blindly.
5. Configure callback access/request logging so authorization codes, state, cookies and full
   query strings are not retained in Worker observability or upstream request logs. Code itself
   emits no logs. Verify this in stage before real consent; do not enable payload capture.
6. After reviewed release only, set operator variable `BACKUP_GOOGLE_OAUTH_ENABLED=enabled`.
   Open `/backup/google`, click connect, select the target Google account, grant `drive.file`.
   Missing configuration returns HOLD. No account creation, OAuth grant or deploy is performed
   merely by merging the code.

Google client credentials cannot be generated by the GitHub or Cloudflare connector. The
Google account owner must complete this Google-side provisioning in its authenticated console.
Do not ask the owner to paste a client-secret JSON, authorization code or refresh token in chat.

## Security and operation

- All page/API routes stay behind the existing single-owner Access checks, including callback.
- Start is same-origin POST plus a custom header. Random state and independent HttpOnly,
  Secure, SameSite=Lax browser cookie are bound in D1 via SHA-256. State expires in 10 minutes
  and is atomically consumed with DELETE RETURNING before token exchange.
- Confidential authorization-code flow uses client secret and exact fixed redirect URI.
- Only `drive.file` is requested; access_type=offline. Missing refresh token/scope is HOLD.
- `about.get` validates actual Google account before persisting credentials. Wrong identity
  cannot replace a prior valid connection. No Drive write is part of this adapter.
- Refresh token is AES-256-GCM sealed with a fresh 96-bit nonce and account/version-bound AAD.
  D1 contains only ciphertext, account ID and verification timestamp; no raw access/refresh token.
- Status exposes no email, tokens, account IDs or connection payload. It reports historical
  callback verification, not current token validity or backup readiness.
- `verifiedDriveAccess` refreshes credentials and rechecks actual identity immediately before
  any future uploader writes. Failure never falls back to the ChatGPT Drive connector.
- A future backup exporter must treat these credential tables as sensitive and design explicit
  handling; the OAuth seal key must never be stored inside an exported SQL snapshot. This key
  is distinct from the future backup encryption/recovery key.
- No automatic token retries or background schedule in this OAuth slice. Invalid/revoked grants
  require reconnect. Rotation: reconnect using a new seal key in a controlled window; do not change
  the key and silently discard the old encrypted connection without recovery/reconnect planning.
- Google External apps in Testing may issue short-lived refresh tokens (commonly seven days);
  validate the current consent publishing mode before claiming unattended durable backups.

## Verification and remaining gate

Run `npm test` (Node 22 or later; node:sqlite is used only by tests). Tests exercise real SQLite
state consumption, expiry, browser mismatch, token sealing/tampering, wrong-account rejection,
missing grants, refresh identity checks, provider failure and Access protection of new routes.

Still requires live Google consent, live callback through Access and secure storage inspection.
Then implement and verify export -> backup encryption -> upload -> read-back -> decrypt ->
isolated D1 restore -> complete schema/row hash comparison. Keep backup status HOLD until that
end-to-end evidence exists. No automatic deletion of the existing same-account recovery copy.

Rollback: disable BACKUP_GOOGLE_OAUTH_ENABLED, restore previous Worker code, retain additive
tables encrypted. Revoke the app grant through Google if abandoning the connection. No table
deletion or token revocation is triggered automatically by this PR.
